# Схема PostgreSQL (ТЗ v12)

Скрипты создают базу данных серверной части по ТЗ v12: учётные записи, цели, задачи,
категории, календарь, учебные данные ОРИОКС, файлы и история запросов к ИИ.
Модель данных описана в документе «kpo_project: роли, модель данных и контракты»;
`database/data_model.md` пока описывает хранилище браузера по ТЗ v11.

Нужен **PostgreSQL 15 или новее**: внешние ключи используют `ON DELETE SET NULL (столбец)`.

## Запуск

Обычно схему ставит первая миграция Alembic (`backend/migrations/versions/0001_initial_schema.py`):
она выполняет скрипты из `install.sql` по порядку.

```sh
createdb planner
uv run --project backend --frozen alembic -c backend/alembic.ini upgrade head   # или: psql -d planner -f database/postgresql/install.sql
psql -d planner -f database/postgresql/tests/test_schema.sql   # последняя строка: «Все проверки пройдены»
```

`install.sql` рассчитан на пустую базу. Чтобы пересоздать схему при разработке:

```sql
DROP SCHEMA planner, analytics CASCADE;
```

Роли общие для всего сервера PostgreSQL и при повторной установке не пересоздаются.

Базу создавайте с локалью UTF-8 (так по умолчанию в образе `postgres` для Docker). При локали `C`
`citext` не приводит кириллицу к одному регистру, и «Учёба» и «УЧЁБА» станут разными категориями.
Например: `createdb -T template0 -E UTF8 --locale-provider=builtin --builtin-locale=C.UTF-8 planner`
(PostgreSQL 17+).

## Пользователи для входа

Роли `planner_app` и `planner_analyst` — наборы прав без права входа. Пользователей создают отдельно:

```sql
CREATE ROLE planner_backend LOGIN PASSWORD '…' IN ROLE planner_app;      -- серверная часть
CREATE ROLE ivanov_analyst  LOGIN PASSWORD '…' IN ROLE planner_analyst;  -- аналитика
ALTER ROLE planner_backend SET search_path = planner;
```

Скрипты выполняет роль-владелец (она же потом выполняет миграции). Серверная часть
подключается под `planner_backend`: читает и меняет данные, но не может менять структуру.
Аналитик видит только представления `analytics.*` без email, имён, паролей, токенов,
названий задач и текстов запросов к ИИ.

## Ошибки для серверной части

| SQLSTATE | Когда | Код API |
|---|---|---|
| `23514` check_violation | Нарушено ограничение `CHECK`; имя ограничения — в тексте ошибки | 422 VALIDATION_ERROR |
| `23505` unique_violation | Email или название категории уже есть | 409 EMAIL_TAKEN / CONFLICT |
| `23503` foreign_key_violation | Ссылка на несуществующую или чужую запись | 404 NOT_FOUND |
| `22P02` invalid_text_representation | Неизвестный статус, приоритет или неверный uuid | 422 VALIDATION_ERROR |
| `AP001` | Объект не найден в функции или процедуре | 404 NOT_FOUND |
| `AP002` | Предложение ИИ уже решено | 409 CONFLICT |
| `AP003` | Неверные данные для операции | 422 VALIDATION_ERROR |

Ограничения в базе — последняя линия защиты. Схемы Pydantic должны отклонять неверные
данные раньше и возвращать понятное сообщение с полем.

## Что важно знать

- **Чужие данные.** У каждой таблицы есть `user_id`, а ссылки между записями — составные
  внешние ключи `(x_id, user_id)`: задача не может сослаться на цель другого пользователя.
  Запросы всё равно обязаны фильтровать по `user_id` текущего пользователя.
- **Файлы.** В базе только описание файла, содержимое лежит в хранилище по `storage_key`.
  Когда строка файла удаляется (в том числе вместе с задачей, целью или пользователем),
  триггер кладёт `storage_key` в `planner.file_deletion_queue`. Фоновая задача сервера
  удаляет файл из хранилища, затем строку из очереди.
- **Текстовые запросы к ИИ** (`COMMAND`) применяет серверная часть обычными запросами
  к таблицам задач и событий; декомпозицию цели — функция `planner.apply_decomposition`.
- **Миграции.** Эти скрипты — первая версия схемы, их выполняет миграция Alembic `0001`.
  После применения скрипты не меняются: структура дальше меняется только новыми миграциями
  в `backend/migrations/versions`.
- **Плановые задачи:** `CALL planner.purge_sessions();` раз в сутки и обработка
  `planner.file_deletion_queue`.
