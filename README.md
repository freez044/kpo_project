# Adaptive AI Planner

Адаптивная система планирования личных задач и целей с использованием искусственного интеллекта. Учебный проект по дисциплине «Конструирование программного обеспечения».

Система предназначена для студентов, которым нужно учитывать учебное расписание, задания и личные дела. ИИ помогает разбить большую цель на задачи, а контроль нагрузки — заранее заметить скопление дедлайнов.

**Статус:** ранний прототип. В репозитории находятся техническая документация, UML-диаграммы, заготовка API задач, модуль локального хранилища и SQL-скрипты. Пользовательский интерфейс и интеграции с внешними сервисами пока не реализованы.

## Возможности по ТЗ

- Управление целями, задачами и категориями; канбан-доска и главная страница с планом на день.
- Календарь учебных занятий, личных событий и интервалов выполнения задач; обнаружение пересечений времени.
- Получение расписания и доступных учебных заданий из ОРИОКС.
- Оценка текущей и будущей нагрузки, предупреждения о близких дедлайнах и рекомендации начать работу заранее.
- ИИ-ассистент для текстовых запросов и декомпозиции целей. Пользователь проверяет, редактирует и подтверждает предложения перед изменением данных.
- Рабочие сессии с заметками, файловые вложения, резервное копирование и восстановление данных.

Это целевые возможности из [ТЗ v10](docs/ТЗ_Adaptive_AI_Planner_v10.docx). Их готовность отражена ниже.

## Архитектура по ТЗ v10

Пользователь работает с приложением в браузере. Интерфейс и локальная логика используют IndexedDB для хранения данных. Запросы к языковой модели и ОРИОКС проходят через сервер FastAPI.

| Компонент | Назначение |
|---|---|
| React и TypeScript | Экраны приложения и взаимодействие с пользователем |
| IndexedDB через Dexie | Хранение профиля, целей, задач, календаря, сессий, файлов и истории ИИ |
| FastAPI | Посредник при обращении к внешним сервисам |
| Внешняя языковая модель | Разбор текстовых запросов и предложения по декомпозиции целей |
| ОРИОКС | Учебное расписание и доступные задания |

По ТЗ пользовательские данные постоянно хранятся в браузере, регистрация не требуется, а сервер не сохраняет запросы и ответы. Содержимое вложений не передаётся языковой модели. Даты, просрочки, прогресс и конфликты времени рассчитываются программной логикой.

Эта архитектура находится на стадии реализации. В документах и SQL-материалах есть расхождения с ТЗ — см. [вопросы согласования](#вопросы-согласования).

## Технологии

- **Backend:** Python 3.13+, FastAPI, Pydantic, Uvicorn; зависимости зафиксированы в `backend/uv.lock`, управление окружением — `uv`.
- **Модуль браузерного хранилища:** TypeScript, Dexie, `dexie-export-import`.
- **SQL-материалы:** PostgreSQL. SQLAlchemy, Psycopg и Pydantic Settings объявлены в зависимостях backend, но пока не используются в коде приложения.
- **Проектирование:** PlantUML.
- **Планируемый интерфейс:** React и TypeScript.

## Запуск backend

Нужны установленные **Python 3.13 или новее** и **uv**. Для установки зависимостей потребуется доступ к реестру пакетов.

Все команды выполняются **из корня репозитория**, где находятся папки `backend`, `database` и `docs`.

1. Установить зависимости из lock-файла:

   ```sh
   uv sync --project backend --frozen
   ```

2. Запустить сервер:

   ```sh
   uv run --project backend --frozen python -m uvicorn app.main:app --app-dir backend
   ```

3. Открыть [Swagger UI](http://127.0.0.1:8000/docs) или [спецификацию OpenAPI](http://127.0.0.1:8000/openapi.json).

Остановить сервер можно сочетанием `Ctrl+C`. Для автоматического перезапуска при изменении кода к команде запуска можно добавить `--reload`.

Запуск из корня нужен из-за смешанных импортов `app.*` и `backend.app.*`. Команда `uv run uvicorn app.main:app --reload`, выполненная внутри `backend`, в текущей версии завершается ошибкой `ModuleNotFoundError: No module named 'backend'`.

Подключение к PostgreSQL, файл `.env` и ключ ИИ для текущего прототипа не требуются: код приложения их пока не использует. Эта команда запускает только backend; веб-интерфейса в репозитории ещё нет.

### Маршруты API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/tasks` | Список задач |
| `GET` | `/tasks/{task_id}` | Получение задачи |
| `POST` | `/tasks` | Создание задачи |
| `PATCH` | `/tasks/{task_id}` | Изменение задачи |
| `DELETE` | `/tasks/{task_id}` | Удаление задачи |

Маршруты зарегистрированы, но основные операции с задачами пока завершаются внутренними ошибками. Причины описаны в [известных проблемах](#известные-проблемы-backend).

## Проверка SQL-скриптов

SQL-скрипты проверяются отдельно от backend. Для этого нужны PostgreSQL и доступные команды `createdb` и `psql`. Проверка выполнена на PostgreSQL 18.

Из корня репозитория создать отдельную пустую учебную базу и выполнить скрипты по порядку:

```sh
createdb -U postgres task_manager
psql -U postgres -d task_manager -v ON_ERROR_STOP=1 -f database/initial_schema.sql
psql -U postgres -d task_manager -v ON_ERROR_STOP=1 -f database/seed_values.sql
psql -U postgres -d task_manager -v ON_ERROR_STOP=1 -f database/test_relations.sql
psql -U postgres -d task_manager -v ON_ERROR_STOP=1 -f database/test_constraints.sql
psql -U postgres -d task_manager -v ON_ERROR_STOP=1 -f database/test_deletion.sql
```

Замените `postgres` своим пользователем PostgreSQL. Если база `task_manager` уже существует и содержит данные, используйте другое имя отдельной пустой базы во всех командах. Схема создаёт таблицы и индексы и не предназначена для повторного применения к уже созданной схеме.

Ожидаемые итоговые сообщения:

```text
ALL RELATION TESTS PASSED
ALL 16 CONSTRAINT TESTS PASSED
ALL 8 DELETION TESTS PASSED
```

Проверки ограничений и удаления откатывают свои тестовые изменения. `seed_values.sql` сохраняет демонстрационные записи.

Файл `database/task_session_migration.sql` **не входит в эту последовательность**: он удаляет таблицу рабочих сессий и оценку длительности цели для перехода к другой модели данных. Следующий за `COMMIT` оператор `ROLLBACK` не отменяет уже зафиксированные изменения. После этой миграции исходные SQL-проверки рабочих сессий неприменимы.

Файлы `seed_values.sql`, `test_relations.sql`, `test_constraints.sql` и `test_deletion.sql` в `tests/database` совпадают с одноимёнными файлами в `database`. Для приведённых команд используется папка `database`.

## Известные проблемы backend

- **Несогласованные поля задачи.** `create_task` обращается к `task.id` и `task.est_duration`, которых нет в `TaskCreate`. Создание задачи завершается `AttributeError`.
- **Несоответствие ответов схемам.** Исходная задача содержит `est_duration`, а `TaskRead` ожидает `estimated_duration_minutes`, `description`, `priority` и `deadline`. Получение списка, чтение, изменение и удаление этой задачи приводят к `ResponseValidationError` и HTTP 500. Идентификатор задачи также отсутствует в `TaskRead`.
- **Частичное обновление.** Обработчик `PATCH` изменяет только название и оценку длительности, хотя схема принимает и другие поля.
- **Статусы отличаются от ТЗ.** В Python-перечислении есть `IN_CREATION` и отсутствует `PLANNED`; в ТЗ, SQL-схеме и модуле IndexedDB используется `PLANNED`.
- **Импорты требуют унификации.** Используются пути `app.*` и `backend.app.*`; в схеме категории указан отдельный импорт `from colors import Colors`.

## Вопросы согласования

В репозитории представлены разные проектные решения. Перед объединением модулей нужно согласовать требования и привести документы, схему и код к одной модели.

| Вопрос | ТЗ v10 и модуль IndexedDB | Модель данных v1.2 и SQL-материалы |
|---|---|---|
| Хранение и учётные записи | Данные в браузере, регистрация не нужна | Модель v1.2 описывает пользователей с email и паролем и хранение в PostgreSQL |
| Рабочие сессии | Предусмотрены сессии, заметки и фактическое время | Модель v1.2 исключает сессии; начальная SQL-схема и тесты ещё содержат `task_session`, отдельная миграция удаляет её |
| Удаление цели | Задачи сохраняются и теряют связь с целью | Модель v1.2, SQL-схема и SQL-тесты предусматривают каскадное удаление задач |
| Оценка длительности цели | Необязательное отдельное поле цели | В модели v1.2 поле исключено; начальная SQL-схема содержит его, миграция удаляет |

Модуль `docs/storage/db.ts` пока не проверен в составе браузерного приложения. Его комментарии также содержат номера функциональных требований, которые местами отличаются от нумерации ТЗ v10.
