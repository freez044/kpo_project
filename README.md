# Adaptive AI Planner

Адаптивная система планирования личных задач и целей с использованием искусственного интеллекта. Учебный проект по дисциплине «Конструирование программного обеспечения».

Система предназначена для студентов, которым нужно учитывать учебное расписание, задания и личные дела. ИИ помогает разбить большую цель на задачи, а контроль нагрузки — заранее заметить скопление дедлайнов.

**Статус:** ранний прототип. В репозитории находятся техническая документация, UML-диаграммы, модель данных, модуль локального хранилища с тестами и заготовка серверной части. Пользовательский интерфейс и интеграции с внешними сервисами пока не реализованы.

## Возможности по ТЗ

- Управление целями, задачами и категориями; канбан-доска и главная страница с планом на день.
- Календарь учебных занятий, личных событий и интервалов выполнения задач; обнаружение пересечений времени.
- Получение расписания и доступных учебных заданий из ОРИОКС.
- Оценка текущей и будущей нагрузки, предупреждения о близких дедлайнах и рекомендации начать работу заранее.
- ИИ-ассистент для текстовых запросов и декомпозиции целей. Пользователь проверяет, редактирует и подтверждает предложения перед изменением данных.
- Учётные записи и работа с одними данными с компьютера, планшета и телефона; просмотр канбан-доски и календаря без интернета.
- Файловые вложения и выгрузка своих данных в файл.

Это целевые возможности из [ТЗ v12](docs/ТЗ_Adaptive_AI_Planner_v12.docx). Их готовность отражена ниже.

## Архитектура по ТЗ v12

В ТЗ v12 архитектура изменена: данные пользователя хранятся на сервере, а не в браузере. Пользователь регистрируется, входит с любого устройства и видит одни и те же данные. Без интернета доступен только просмотр канбан-доски и календаря.

| Компонент | Назначение |
|---|---|
| React и TypeScript | Экраны приложения; адаптивная вёрстка для компьютера, планшета и телефона |
| FastAPI | REST API: учётные записи, данные пользователя, обращения к языковой модели и ОРИОКС |
| PostgreSQL | Хранение профиля, целей, задач, категорий, календаря, учебных заданий, истории ИИ |
| Файловое хранилище сервера | Прикреплённые файлы |
| IndexedDB | Копия канбан-доски и календаря для просмотра без сети |
| Внешняя языковая модель | Разбор текстовых запросов и предложения по декомпозиции целей |
| ОРИОКС | Учебное расписание и задания; ключ доступа хранится на сервере в зашифрованном виде |

Содержимое вложений не передаётся языковой модели. Даты, просрочки, прогресс и конфликты времени рассчитываются программной логикой.

UML-диаграммы и схема базы данных (`database/postgresql`) описывают архитектуру ТЗ v12. Текст `database/data_model.md` и модуль `docs/storage/db.ts` пока описывают хранилище браузера по ТЗ v11 и будут обновлены.

## Технологии

- **Backend:** Python 3.13+, FastAPI, Pydantic, Uvicorn; зависимости зафиксированы в `backend/uv.lock`, управление окружением — `uv`.
- **Модуль браузерного хранилища:** TypeScript, Dexie, `dexie-export-import`.
- **Слой данных:** PostgreSQL 15+, SQLAlchemy 2, Psycopg и Alembic. Модели и базовые репозитории реализованы; подключение к ранним HTTP-маршрутам ещё предстоит.
- **Проектирование:** PlantUML.
- **Планируемый интерфейс:** React и TypeScript.

## Запуск backend

Нужны установленные **Python 3.13 или новее** и **uv**. Для установки зависимостей потребуется доступ к реестру пакетов.

Все команды выполняются **из корня репозитория**, где находятся папки `backend`, `database` и `docs`.

1. Установить зависимости из lock-файла:

   ```sh
   uv sync --project backend --frozen
   ```

2. Запустить сервер:

   ```sh
   uv run --project backend --frozen python -m uvicorn app.main:app --app-dir backend
   ```

3. Открыть [Swagger UI](http://127.0.0.1:8000/docs) или [спецификацию OpenAPI](http://127.0.0.1:8000/openapi.json).

Остановить сервер можно сочетанием `Ctrl+C`. Для автоматического перезапуска при изменении кода к команде запуска можно добавить `--reload`.

Запуск из корня нужен из-за смешанных импортов `app.*` и `backend.app.*`. Команда `uv run uvicorn app.main:app --reload`, выполненная внутри `backend`, в текущей версии завершается ошибкой `ModuleNotFoundError: No module named 'backend'`.

Для ранних маршрутов `/tasks` PostgreSQL и ключ ИИ не требуются: они работают со списком в памяти. Слой данных требует PostgreSQL, настройки `DATABASE_URL` и миграции; команды приведены в [CLAUDE.md](CLAUDE.md) и [описании БД](database/postgresql/README.md). Эта команда запускает только backend; веб-интерфейса в репозитории ещё нет.

### Маршруты API

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/tasks` | Список задач |
| `GET` | `/tasks/{task_id}` | Получение задачи |
| `POST` | `/tasks` | Создание задачи |
| `PATCH` | `/tasks/{task_id}` | Изменение задачи |
| `DELETE` | `/tasks/{task_id}` | Удаление задачи |

Маршруты зарегистрированы, но основные операции с задачами пока завершаются внутренними ошибками. Причины описаны в [известных проблемах](#известные-проблемы-backend).

## Проверка хранилища

Модуль `docs/storage/db.ts` проверяется тестами `docs/storage/db.test.ts` (vitest + fake-indexeddb): удаление задач и целей со связанными данными, проверки полей, календарь и пересечения, файлы, история запросов к ИИ, резервная копия, включая обрезанный и чужой файл. До создания каркаса фронтенда тесты запускались отдельно на Dexie 4.4.1 и fake-indexeddb 6.2.6: все 14 проходят. Порядок запуска — в [описании хранилища](docs/storage/README.md).

## Известные проблемы backend

- **Несогласованные поля задачи.** `create_task` обращается к `task.id` и `task.est_duration`, которых нет в `TaskCreate`. Создание задачи завершается `AttributeError`.
- **Несоответствие ответов схемам.** Исходная задача содержит `est_duration`, а `TaskRead` ожидает `estimated_duration_minutes`, `description`, `priority` и `deadline`. Получение списка, чтение, изменение и удаление этой задачи приводят к `ResponseValidationError` и HTTP 500. Идентификатор задачи также отсутствует в `TaskRead`.
- **Частичное обновление.** Обработчик `PATCH` изменяет только название и длительность, хотя схема принимает и другие поля.
- **Маршруты требуют приведения к ТЗ v12.** Пользовательские данные хранятся на сервере; ранние `/tasks` нужно подключить к PostgreSQL и привести к `/api/v1/tasks`, схемам и правилам доступа из `docs/contracts.md`.
- **Импорты требуют унификации.** Используются пути `app.*` и `backend.app.*`; в схеме категории указан отдельный импорт `from colors import Colors`.
