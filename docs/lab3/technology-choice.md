# Выбор и обоснование технологий — ЛР №3

Документ закрывает пункты 1–2 раздела «Порядок выполнения лабораторной работы»: перечисляет технологии Adaptive AI Planner и объясняет их назначение, удобство и ограничения. Основание — [ТЗ v12](../ТЗ_Adaptive_AI_Planner_v12.docx), [контракты API](../contracts.md), [UML](../uml/README.md) и состав репозитория на `d6f4ebb397323839fe12bf00bec3b4d0431987e4`.

Это выбор платформы для проекта. Наличие технологии в таблице не означает, что соответствующий модуль уже реализован. Работы, зависимости и критерии готовности перечислены в [плане разработки](development-plan.md).

## 1. Требования, определяющие выбор

- Приложение работает в браузере на компьютере, планшете и телефоне; интерфейс адаптируется к ширине от 360 точек.
- Пользователь входит с разных устройств и получает одинаковые данные. Основное хранилище находится на сервере; без сети доступен только просмотр копии канбана и календаря (ФТ-02, ФТ-42).
- Есть связанные сущности и операции над несколькими записями: пользователи, цели, задачи, категории, календарь, файлы, учебные данные и предложения ИИ. Нужны ограничения целостности и транзакции (НД-03, НД-04).
- Сервер обращается к внешним API ИИ и ОРИОКС. Их недоступность не должна блокировать ручную работу. Бюджет внешней операции — до 60 секунд, включая не более двух повторных запросов (НД-01).
- При объёме до 1000 задач на пользователя и до 20 одновременных пользователей целевое время обычных операций — до 1 секунды. Это требование для проверки, а не уже измеренный результат.
- Пять участников должны разрабатывать части параллельно по согласованным интерфейсам и объединять результаты через Git.

## 2. Перечень технологий и обоснование

| Технология | Для чего используется | Почему подходит проекту и чем удобна | Ограничение и состояние |
|---|---|---|---|
| **Веб-приложение React + TypeScript** | Формы, канбан, календарь, цели, ИИ-ассистент и профиль | Компоненты позволяют разделить экраны между двумя разработчиками; TypeScript помогает согласовать формы JSON с API; одна клиентская часть обслуживает разные устройства | Нужны адаптивность и браузерные проверки. Типы не заменяют серверную валидацию. Каркас ещё предстоит создать |
| **Python 3.13+ и FastAPI** | HTTP API, учётные записи, бизнес-логика и внешние интеграции | Совместимы с уже выбранным Python-стеком; маршруты и зависимости удобно разделить по сервисам; OpenAPI помогает двум фронтенд-разработчикам работать по контракту | Ранние маршруты уже есть, но требуют подключения к БД и приведения к контракту. Производительность проверяется отдельно |
| **Pydantic** | Схемы входных/выходных данных, настройки, проверка предложений ИИ | Общие схемы помогают проверять обязательные поля, перечисления и структуру JSON; правила API становятся явными | Бизнес-правила, права доступа и существование связанных объектов проверяет также серверный сервис и БД |
| **Uvicorn** | Запуск ASGI-приложения FastAPI | Уже входит в окружение backend, подходит для локального запуска и контейнера сервера | Режим разработки и запуск в развёрнутом окружении нужно настроить отдельно |
| **PostgreSQL 15+** | Основное хранилище всех пользователей | Реляционная модель соответствует связям сущностей; внешние ключи, ограничения и транзакции помогают сохранять целостность; составные ссылки с user_id поддерживают изоляцию данных | Нужны сервер, резервные копии и сопровождение. Нижняя граница версии обусловлена используемым DDL, включая ON DELETE SET NULL для выбранных столбцов. Схема уже есть |
| **SQLAlchemy 2 и Psycopg** | Модели, соединения и репозитории над PostgreSQL | Слой данных отделяет хранение от HTTP и позволяет одинаково обслуживать API задач, ИИ и планирование; репозитории можно проверять независимо | ORM не отменяет понимание SQL, транзакций и фильтрации по пользователю. Базовые модели и четыре репозитория уже добавлены |
| **Alembic** | Управляемое изменение схемы БД | Миграции дают одинаковую схему всем участникам и воспроизводимый переход между версиями | Применённые миграции сохраняются; изменение схемы оформляется новой миграцией. Начальная миграция уже есть |
| **uv и uv.lock** | Зависимости и окружение backend | Lock-файл фиксирует разрешённые версии; команда может воспроизводить окружение из корня проекта | Нужна установка инструмента и доступ к пакетам при первой синхронизации. Используются в backend |
| **IndexedDB, Dexie и PWA** | Копия канбана и календаря для просмотра без сети | IndexedDB подходит для структурированной копии, Dexie упрощает работу с таблицами; PWA позволяет подготовить загрузку приложения и сценарий просмотра без сети | По v12 копия доступна только для чтения и очищается при выходе. Старый модуль Dexie нельзя считать готовой реализацией этого режима |
| **Файловое хранилище сервера** | Вложения к задачам и целям | Позволяет хранить содержимое отдельно от реляционных метаданных, отдавая его через проверяющий права API | Нужны ограничения размеров/типов, постоянный том, очистка удалённых файлов и согласованная резервная копия вместе с БД. Реализация впереди |
| **Внешняя LLM через LLMAdapter** | Текстовые команды и предложения по декомпозиции | Внешний API уменьшает объём учебного проекта: обучение своей модели не требуется. Адаптер отделяет поставщика от бизнес-логики и позволяет начать с заглушки | Поставщик/модель выбираются по бюджету, условиям обработки данных, качеству JSON и времени ответа. Требуются проверка ответа, тайм-ауты и подтверждение пользователя. Интеграция ещё не реализована |
| **API ОРИОКС** | Учётная запись, расписание и учебные задания | Используется предусмотренный ТЗ источник учебных данных. Отдельный адаптер отделяет его формат от модели приложения | Нужны преобразование недель в даты, обновление без дублей и обработка отказов. Формат резервного файла согласуется отдельно. Интеграция впереди |
| **REST, JSON и OpenAPI** | Общий интерфейс браузера и сервера | Явные маршруты, схемы и ошибки позволяют разрабатывать UI на моках и затем подключить сервер | UUID, camelCase и часовые пояса должны соответствовать contracts.md. Текущий OpenAPI описывает только ранние маршруты |
| **Git, GitHub и Projects** | История, ветки, PR, ревью и задачи | Позволяют пяти участникам независимо работать и связывать задачи с изменениями; история подходит для демонстрации ЛР3 | Роли и метки не заменяют приоритеты/зависимости. Нужны личные изменения каждого участника. Репозиторий, история и доска уже есть |
| **PlantUML** | Сущности, сервисы, компоненты и сценарии | Текстовые исходники диаграмм хранятся в Git и позволяют обсуждать архитектуру до готовности модулей | Исходники и экспортированные изображения должны обновляться согласованно. Диаграммы уже есть |
| **Docker и CI/CD** | Воспроизводимый запуск и автоматические проверки | Контейнеры уменьшают различия окружений команды, а CI проверяет изменения до объединения | Контейнер не заменяет настройку HTTPS, томов, секретов и резервных копий. | **pytest, SQL-проверки, Vitest/fake-indexeddb** | Проверки backend, ограничений БД и браузерной копии | Позволяют проверять слой данных отдельно от HTTP и UI; уже есть материалы для расширения набора проверок | Имеющиеся проверки не подтверждают готовность всего приложения. Конкретные версии backend определяются [pyproject.toml](../../backend/pyproject.toml) и lock-файлом, а не словом «последняя». Версии React/TypeScript, клиентского сборщика, контейнерных образов и CI закрепляются при создании соответствующих окружений. Имена поставщика ИИ и хостинга не подменяются фиктивным выбором.

## 3. Рассмотренные альтернативы

| Решение | Альтернатива | Причина принятого выбора |
|---|---|---|
| Веб-клиент | Отдельные приложения для каждой ОС | Для учебной команды один браузерный интерфейс сокращает число платформ реализации и соответствует ТЗ |
| PostgreSQL как основное хранилище | Только IndexedDB в браузере | Данные должны быть одинаковыми на разных устройствах; браузерная база остаётся копией для просмотра без сети |
| PostgreSQL на сервере | SQLite | Уже разработаны PostgreSQL-схема, функции и миграции; PostgreSQL соответствует принятому общему серверному хранению и правилам изоляции |
| FastAPI | Другой серверный фреймворк | Уже есть Python-код, Pydantic и слой SQLAlchemy; смена фреймворка сейчас потребует переноса основы без выявленной необходимости |
| Внешняя LLM через адаптер | Обучение собственной модели | Цель проекта — планировщик и работа с предложениями; обучение модели существенно расширяет объём и не входит в ТЗ v12 |
| Один серверный экземпляр и модули внутри приложения | Отдельные микросервисы | При заданном масштабе достаточно раздельных модулей и контрактов; отдельные сетевые сервисы усложнят развёртывание и транзакции |

Это обоснование проектных решений. Сравнительный бенчмарк фреймворков и измерение превосходства одной технологии не проводились.

## 4. Проверка выбора по критериям платформы

| Критерий | Как учитывается | Как подтвердить |
|---|---|---|
| Стоимость и объём работы | Используются уже подготовленные Python/SQL-материалы, один веб-клиент и внешний ИИ вместо обучения модели | Оценить задачи; перед подключением LLM и хостинга выбрать допустимый бюджет и условия. Тарифы не зафиксированы |
| Производительность | Индексы, серверная фильтрация, заданный ограниченный объём данных | L3-36: до 20 одновременных пользователей, до 1000 задач на пользователя, обычные операции до 1 с, внешние — до 60 с |
| Надёжность | Транзакции, ограничения БД, ежедневные копии, обработка отказов внешних API | L3-34/L3-36/L3-37/L3-38: откат неуспешной операции, восстановление копии, перезапуск и ручная работа при сбоях интеграций |
| Масштабируемость | Модули отделены от HTTP и хранения, поставщик ИИ вынесен в адаптер | Сначала подтвердить целевой масштаб одного сервера; дальнейшее увеличение нагрузки оценивается по измерениям |
| Совместимость | Браузер, JSON, OpenAPI, UUID, ISO 8601 с часовым поясом | L3-33/L3-35: согласованные ответы API, экраны от 360 точек, браузеры из ТЗ и переходы между устройствами |
| Параллельная работа команды | Владельцы модулей, явные зависимости, моки и ветки Git | L3-02/L3-33/L3-41–L3-45: согласование интерфейсов, интеграционные сценарии и личная история каждого |

## 5. Программно-аппаратная платформа

Параметры ниже перенесены из п. 5.4 ТЗ как целевые требования. Достаточность конфигурации проверяется после реализации.

| Часть | Требования ТЗ |
|---|---|
| Клиент на компьютере | Windows 10/11 x64, macOS или Linux; 2 ядра от 2 ГГц, от 4 ГБ RAM (рекомендуется 8 ГБ), экран от 1366×768 |
| Телефон/планшет | Android, iOS или iPadOS; ширина от 360 точек |
| Браузер | Последние две основные версии Chrome, Яндекс Браузера, Edge Chromium или Safari, включая предусмотренные мобильные варианты |
| Копия без сети | Не менее 100 МБ свободного места в хранилище браузера; только просмотр последней копии |
| Сервер | Linux/Docker, от 2 vCPU, 2 ГБ RAM и 20 ГБ диска; постоянный интернет, домен и HTTPS; размещение по требованиям п. 5.4.3 ТЗ |

Список ОС и браузеров задаёт область проверки; текущая ветка с документацией не подтверждает, что приложение уже работает на каждой комбинации.

## 6. Что уже есть и что предстоит

- **Есть:** FastAPI-каркас, зависимости backend, PostgreSQL-схема, миграция Alembic, модели и репозитории пользователей/категорий/целей/задач, проверки слоя данных и SQL, UML и текстовые контракты.
- **Требует доведения:** ранние HTTP-маршруты используют список в памяти, их поля расходятся со схемами; новый слой данных ещё нужно подключить к сервисам/API. Старый Dexie-модуль соответствует прежней роли локального хранилища.
- **Предстоит:** React-приложение, полноценная авторизация и остальные API, внешний ИИ и ОРИОКС, Docker/CI/CD, развёртывание, режим просмотра без сети по v12 и комплексные проверки.

Консультации, занятия других групп и push-напоминания на iPhone остаются отдельной черновой идеей. Этот документ обосновывает платформу для действующего ТЗ v12 и не расширяет его функциональные требования.

Для защиты: «Мы выбрали браузерный клиент React/TypeScript и сервер FastAPI с PostgreSQL, потому что нужны разные устройства, единые данные и транзакционные операции. По контрактам два разработчика интерфейса могут работать на моках, пока серверные модули реализуются отдельно. Выбранную конфигурацию проверим по ограничениям времени ответа и объёму данных из ТЗ».
