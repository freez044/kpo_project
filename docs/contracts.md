# Контракты Adaptive AI Planner (ТЗ v12)

Источник правды для всех, кто пишет код: REST API между браузером и сервером, формат ошибок,
схема предложений ИИ и правила работы ИИ-модуля. Модель данных описана в
[`database/postgresql`](../database/postgresql/) (таблицы, ограничения, функции), сценарии —
в [UML-диаграммах](uml/README.md). Когда Бэк 2 опишет маршруты в Pydantic, источником правды
для API станет `/openapi.json` сервера, а этот файл будет обновляться вместе с ним.

## Архитектура в двух словах

- Все данные пользователя хранятся на сервере в PostgreSQL; файлы — в файловом хранилище сервера.
- Пользователь регистрируется и входит по email и паролю, с любого устройства видит одни и те же данные.
- Браузер работает с данными только через REST API. В браузере (IndexedDB) хранится лишь копия
  канбан-доски и календаря для просмотра без сети (ФТ-42); изменять данные без сети нельзя.
- К языковой модели и ОРИОКС обращается только сервер. Ключ LLM и ключи доступа ОРИОКС в браузер не попадают.

## Владельцы контрактов

| Контракт | Между кем | Владелец |
|---|---|---|
| REST API (этот файл, затем OpenAPI) | API-клиент в браузере ↔ сервер | Бэк 2 |
| Модель данных и миграции | Слой данных ↔ все сервисы | Тимлид |
| Функции слоя данных | Сервисы ↔ слой данных | Тимлид |
| Схемы ответов ИИ и предложений | ИИ-модуль ↔ экран ИИ-ассистента | Тимлид |
| Копия для просмотра без сети | Сервер ↔ копия в IndexedDB | Фронт 1 и Бэк 2 |
| Окружение и секреты (`.env.example`) | Сервер и все, кто его запускает | Бэк 3 |

Правила изменения:

1. Контракт меняет только владелец, через PR с меткой `contract`.
2. Такой PR одобряют все стороны контракта.
3. Схема БД меняется только новой миграцией Alembic; старые миграции не правятся.
4. Ломающие изменения API сначала обсуждаются на синке. Пока реализации нет, стороны работают на моках по контракту.

## Соглашения REST API

- База — `/api/v1`; тела в JSON, поля в camelCase (в Pydantic — `alias_generator=to_camel`), id — uuid строкой.
  В базе данных те же поля в snake_case.
- Время — ISO 8601 с часовым поясом; статусы и приоритеты — коды из таблицы 1 ТЗ
  (`BACKLOG`, `PLANNED`, `IN_PROGRESS`, `IN_HOLD`, `DONE`, `CANCELLED`; `LOW`, `MEDIUM`, `HIGH`, `URGENT`;
  цели — `ACTIVE`, `IN_HOLD`, `COMPLETED`, `CANCELLED`).
- PATCH принимает только меняемые поля; `null` очищает необязательное поле (например, `goalId: null` убирает задачу из цели).
- Чужой объект отвечает 404, а не 403, чтобы не раскрывать его существование.
- Списки без постраничной разбивки: по ТЗ у пользователя до 1000 задач.

## Авторизация

- Access-токен — JWT на 15 минут, передаётся в заголовке `Authorization: Bearer` и хранится только
  в памяти страницы, не в localStorage.
- Refresh-токен — случайная строка на 30 дней в cookie `HttpOnly`, `Secure`, `SameSite=Strict`
  с путём `/api/v1/auth`. При каждом обновлении выдаётся новый, старый отзывается; в базе хранится
  только хеш (таблица `sessions`).
- Получив `401 UNAUTHORIZED`, API-клиент один раз вызывает `/auth/refresh` и повторяет запрос;
  если и это не удалось — показывает вход.
- После 5 неудачных попыток входа подряд вход блокируется на 15 минут (ФТ-41;
  процедуры `register_login_failure` и `register_login_success`).
- Пароль — не короче 8 символов, хранится только как хеш argon2id. Email приводится к нижнему регистру.

## Примеры

### Регистрация

```json
POST /api/v1/auth/register
{
  "email": "student@example.com",
  "password": "••••••••••",
  "firstName": "Иван",
  "lastName": "Иванов",
  "studyGroup": "ПИН-31",
  "timezone": "Europe/Moscow"
}
```

`studyGroup` необязательна; при подключении ОРИОКС сервер перезаписывает её группой из профиля студента в ОРИОКС.
Ответ 201 (вход отвечает так же, но кодом 200), refresh-токен приходит в cookie:

```json
{
  "accessToken": "eyJhbGciOi...",
  "expiresIn": 900,
  "user": {
    "id": "0f8c6a52-6c3e-4c1e-9a5b-2f2d1b7e9c11",
    "email": "student@example.com",
    "firstName": "Иван",
    "lastName": "Иванов",
    "studyGroup": "ПИН-31",
    "timezone": "Europe/Moscow",
    "aiHistoryEnabled": true
  }
}
```

### Задача

```json
{
  "id": "6b1f4e0a-2d7c-4b8e-9f31-0c5a7d9e2b44",
  "title": "Описать модель данных",
  "description": "",
  "status": "PLANNED",
  "priority": "HIGH",
  "deadline": "2026-11-10T20:59:00Z",
  "goalId": "8f1c2a7e-3b4d-4c5e-9f60-1a2b3c4d5e6f",
  "categoryId": null,
  "durationMinutes": 120,
  "sortOrder": 1,
  "source": "AI",
  "completedAt": null,
  "isOverdue": false,
  "createdAt": "2026-10-30T09:05:00Z",
  "updatedAt": "2026-10-30T09:05:00Z"
}
```

`isOverdue` вычисляет сервер (ФТ-31). При переводе в `DONE` база сама ставит `completedAt`,
при выходе из `DONE` — очищает (триггер, ФТ-30).

### Копия для просмотра без сети

API-клиент вызывает `GET /offline-snapshot?days=28` после входа и после каждого изменения данных
и целиком заменяет копию в IndexedDB.

```json
{
  "generatedAt": "2026-10-30T10:00:00Z",
  "calendarFrom": "2026-10-23",
  "calendarUntil": "2026-11-27",
  "categories": [{ "id": "…", "name": "Учёба", "color": "#4A6FA5" }],
  "goals": [{ "id": "…", "title": "Сдать курсовую по КПО" }],
  "tasks": [{ "id": "…", "title": "Описать модель данных", "status": "PLANNED", "priority": "HIGH",
              "deadline": "2026-11-10T20:59:00Z", "goalId": "…", "categoryId": null, "isOverdue": false }],
  "calendar": { "events": [], "scheduleItems": [], "lessons": [] }
}
```

`generatedAt` — время последней синхронизации, `calendarUntil` — дата, до которой заполнен календарь (ФТ-42).
Без сети интерфейс показывает обе даты и прячет кнопки изменения. Копия удаляется при выходе из учётной записи (п. 5.8.1).

## Ошибки

Один формат для всех маршрутов; `message` — по-русски и без внутренних подробностей (п. 5.8.2),
логику браузер строит по `code`.

```json
{ "error": { "code": "VALIDATION_ERROR", "message": "Укажите название задачи", "field": "title" } }
```

| HTTP | code | Когда |
|---|---|---|
| 422 | `VALIDATION_ERROR` | Тело запроса не по схеме или недопустимые значения (НД-04) |
| 401 | `UNAUTHORIZED` | Нет access-токена или он истёк |
| 401 | `INVALID_CREDENTIALS` | Неверный email или пароль |
| 429 | `TOO_MANY_ATTEMPTS` | Вход временно заблокирован после неудачных попыток |
| 409 | `EMAIL_TAKEN` | Email уже зарегистрирован |
| 404 | `NOT_FOUND` | Объекта нет или он чужой |
| 409 | `CONFLICT` | Категория с таким названием уже есть; предложение ИИ уже решено |
| 413 | `FILE_TOO_LARGE` | Файл больше лимита (приложение В ТЗ) |
| 415 | `UNSUPPORTED_FILE_TYPE` | Недопустимый тип файла |
| 409 | `ORIOKS_NOT_CONNECTED` | ОРИОКС не подключён |
| 400 | `ORIOKS_AUTH_FAILED` | Неверный логин или пароль ОРИОКС, ключ доступа отозван — нужно подключиться заново |
| 409 | `ORIOKS_TOKEN_LIMIT` | У студента уже 8 ключей доступа ОРИОКС |
| 503 | `ORIOKS_UNAVAILABLE` | ОРИОКС не ответил за отведённое время |
| 503 | `AI_UNAVAILABLE` | LLM недоступна |
| 504 | `AI_TIMEOUT` | Операция с ИИ не уложилась в 60 с |
| 502 | `AI_BAD_RESPONSE` | Ответ модели не прошёл проверку после повторов |
| 429 | `RATE_LIMITED` | Слишком много запросов |
| 500 | `INTERNAL_ERROR` | Прочие сбои сервера |

Ошибки ОРИОКС отвечают не кодом 401: иначе API-клиент принял бы их за истёкший access-токен и попытался обновить сеанс.

Перевод ошибок базы данных в коды API:

| SQLSTATE | Код API |
|---|---|
| `23514` check_violation, `22P02` invalid_text_representation, `AP003` | 422 `VALIDATION_ERROR` |
| `23505` unique_violation | 409 `EMAIL_TAKEN` (users) или `CONFLICT` |
| `23503` foreign_key_violation, `AP001` | 404 `NOT_FOUND` |
| `AP002` | 409 `CONFLICT` |

## ИИ-модуль

ИИ-модуль целиком на сервере (владелец — тимлид): сервер сам собирает контекст из базы, вызывает модель,
проверяет ответ и применяет предложение одной транзакцией. Браузер только показывает предложение и даёт его поправить.

| Шаг | Где | Что происходит |
|---|---|---|
| 1. Запрос | Экран ИИ-ассистента или цели | `POST /ai/command` с текстом или `POST /ai/decompose` с `goalId` |
| 2. Контекст | AIService | Для command — названия целей, категорий, задач и событий на 14 дней вперёд; для decompose — название и описание цели |
| 3. Вызов модели | LLMAdapter | Промпт и JSON-схема ответа, ключ из переменной окружения; 60 с на всю операцию, не более двух повторов (НД-01) |
| 4. Проверка | AIService | Формат по схеме, допустимые значения, ссылки только на объекты этого пользователя (ФТ-38) |
| 5. Сохранение | Слой данных | Запись в `ai_proposals` со статусом `PENDING` |
| 6. Показ и правки | Экран | Ответ 201 с предложением; пользователь правит, добавляет, удаляет пункты (ФТ-39) |
| 7. Применение | AIService | `/apply` повторно проверяет данные и в одной транзакции создаёт или меняет объекты, ставит `ACCEPTED` или `EDITED` |

`EDITED` сервер ставит сам, если `finalData` отличается от ответа модели. Если пользователь отключил историю (ФТ-40),
запись предложения удаляется сразу после решения. Декомпозицию применяет функция БД `planner.apply_decomposition`,
отклонение — процедура `planner.reject_proposal`; текстовые команды применяет код сервиса.

### Предложение

```json
{
  "id": "5d6e7f80-91a2-4b3c-8d4e-5f6071829304",
  "kind": "DECOMPOSE",
  "status": "PENDING",
  "goalId": "8f1c2a7e-3b4d-4c5e-9f60-1a2b3c4d5e6f",
  "requestText": "Сдать курсовую по КПО",
  "result": {
    "comment": "Цель разбита на 4 этапа",
    "tasks": [
      { "title": "Описать модель данных", "description": "Таблицы, связи, правила удаления",
        "order": 1, "priority": "HIGH", "durationMinutes": 120 }
    ]
  },
  "model": "provider/model-name",
  "latencyMs": 8200,
  "createdAt": "2026-10-30T09:05:00Z"
}
```

- `DECOMPOSE`: от 1 до 20 задач; `title` до 200 символов; `order` — 1..N без повторов; `durationMinutes` —
  от 1 до 1440 или отсутствует; конкретные даты не обязательны (ФТ-37).
- `COMMAND`: `result = { action, kind, targetId?, fields }`, где `action` — `CREATE`, `UPDATE` или `CLARIFY`,
  `kind` — `TASK` или `EVENT`. При `CLARIFY` вместо полей приходит `message` с уточняющим вопросом.
- Событие без времени окончания (ФТ-36 это допускает) получает начало + 60 минут; это видно в карточке до подтверждения.
- `/apply` принимает `{ finalData }` той же формы, что `result`, и возвращает созданные и изменённые объекты.

### Что уходит в языковую модель

- Для декомпозиции — название и описание цели, текущие дата и часовой пояс.
- Для текстового запроса — текст, дата, часовой пояс, названия и сроки целей, категорий, задач и событий.
  Вместо uuid модель видит короткие метки (`g1`, `t3`, `e2`), сервер переводит их обратно.
- Не уходят: email, имя, фамилия, группа, содержимое файлов, ключ и данные ОРИОКС, история запросов.

### LLMAdapter

- Интерфейс с двумя методами, `decompose` и `command`: модель можно заменить, не трогая остальное (п. 4.2 ТЗ).
  Для разработки есть заглушка с фиксированными ответами.
- Ключ и название модели — только в переменных окружения (`LLM_API_KEY`, `LLM_MODEL`).
- Промпты и JSON-схемы лежат в репозитории рядом с адаптером и меняются через PR с меткой `contract`.
- В журнал пишутся только метаданные вызова: модель, время, код ошибки; тексты запросов и ответов — нет.

## ОРИОКС

- Подключение (`POST /orioks/connection`): сервер получает ключ доступа по логину и паролю ОРИОКС
  (`GET /api/v1/auth` в API ОРИОКС), находит числовой id группы и дату начала семестра, шифрует ключ
  (AES-GCM, ключ шифрования — в переменной окружения) и сохраняет в `orioks_connections`. Пароль ОРИОКС не хранится.
- Расписание ОРИОКС отдаёт по типу недели, дню и номеру пары; сервер переводит их в реальные даты семестра
  и заменяет занятия процедурой `planner.replace_lessons`.
- У контрольных мероприятий ОРИОКС нет ни id, ни даты, только номер недели. Сервер собирает
  `externalId = дисциплина:вид:неделя`, срок — конец учебной недели, и обновляет задания процедурой
  `planner.upsert_assignments`.
- Документация API ОРИОКС: <https://orioks.gitlab.io/student-api/>.
